# DeskMate Link v1

Status: `DESKMATE_LINK_V1_FROZEN`

## Roles and physical layer

- EasyInput is the only controller and request initiator. Xiaozhi is the responder.
- UART is 115200 baud, 8 data bits, no parity, 1 stop bit, no flow control.
- EasyInput J4 uses `TXD0/GPIO43`, `RXD0/GPIO44`, and `GND` only. J4 `3V3` remains disconnected.
- The boards use independent power and a common ground. TX and RX are crossed.
- UART0 carries DeskMate Link bytes only after application startup. Application and bootloader logs are disabled. ROM startup noise cannot be disabled without irreversible configuration, so both parsers must discard noise and resynchronize on the frame magic.

## Frame

All multi-byte integers are little-endian.

| Offset | Bytes | Field |
| ---: | ---: | --- |
| 0 | 4 | ASCII magic `DMLK` (`44 4D 4C 4B`) |
| 4 | 1 | Version, fixed `0x01` |
| 5 | 1 | Flags |
| 6 | 1 | Message type |
| 7 | 1 | Reserved, fixed `0x00` |
| 8 | 4 | Non-zero sequence |
| 12 | 2 | Payload length, `0..128` |
| 14 | N | Payload |
| 14+N | 2 | CRC16-CCITT-FALSE |

- Maximum frame size is 144 bytes.
- CRC polynomial is `0x1021`, initial value `0xFFFF`, no reflection and no final XOR.
- CRC covers bytes from version at offset 4 through the last payload byte. It excludes magic and the CRC field.
- Flags are exactly one of request `0x01`, response `0x02`, or error `0x04`. Other bits and combinations are invalid.
- A parser scans for `DMLK`, accepts fragmented and concatenated frames, and abandons an incomplete candidate after 100 ms without a byte.
- Bad magic, oversized length, timeout, bad CRC, unsupported version, non-zero reserved byte, or invalid flags are dropped and counted. They do not produce a reply because the frame identity is not trusted.
- A CRC-valid semantic error returns an error frame with the original sequence and message type and a one-byte error payload.

## Messages

### `0x01 HELLO`

Request payload, 7 bytes:

| Field | Type | Value |
| --- | --- | --- |
| role | u8 | controller `1` |
| min_version | u8 | `1` |
| max_version | u8 | `1` |
| controller_boot_id | u32 | random non-zero boot epoch |

Response payload, 8 bytes:

| Field | Type | Value |
| --- | --- | --- |
| role | u8 | Xiaozhi responder `2` |
| selected_version | u8 | `1` |
| peer_boot_id | u32 | random non-zero boot epoch |
| max_payload | u16 | `128` |

### `0x02 GET_CAPABILITIES`

The request payload is empty. The response is 10 bytes: `implemented:u32`, `enabled:u32`, `max_payload:u16`.

Capability bits:

| Bit | Name | Meaning |
| ---: | --- | --- |
| 0 | `LINK_CORE` | v1 framing, lifecycle and read-only status |
| 1 | `AGENT_STATE` | `SET_AGENT_STATE` storage/acknowledgement |
| 2 | `DISPLAY` | future OLED execution slice |
| 3 | `MOTION` | future servo execution slice |
| 4 | `AUDIO` | future Xiaozhi audio slice |

`enabled` must be a subset of `implemented`. T08 requires `LINK_CORE` and `AGENT_STATE` in both masks and requires `max_payload=128`. DISPLAY, MOTION and AUDIO remain clear in T08.

### `0x03 GET_STATUS`

The request payload is empty. The response is 11 bytes:

| Field | Type | Meaning |
| --- | --- | --- |
| peer_boot_id | u32 | must match HELLO |
| uptime_ms | u32 | wrapping monotonic milliseconds |
| agent_state | u8 | enum below |
| status_flags | u8 | bits below |
| last_error | u8 | last semantic error, or `0` |

Agent states: idle `0`, listening `1`, thinking `2`, working `3`, waiting `4`, completed `5`, error `6`.

Status flags: link_ready bit 0, display_ready bit 1, motion_ready bit 2, audio_enabled bit 3, faulted bit 7. Bits 4–6 are zero in v1.

### `0x04 SET_AGENT_STATE`

Request and successful response are both 5 bytes: `transition_id:u32` followed by `agent_state:u8`. The response must echo the accepted transition and state. T08 implements this wire/API boundary but does not connect it to the desktop or execute display/motion actions.

## Errors

An error response uses flag `0x04`, the request's sequence and type, and exactly one error byte:

| Value | Name |
| ---: | --- |
| 1 | `UNKNOWN_TYPE` |
| 2 | `BAD_PAYLOAD` |
| 3 | `NOT_READY` |
| 4 | `BUSY` |
| 5 | `SEQUENCE_CONFLICT` |
| 6 | `INTERNAL` |

## Lifecycle, retry and idempotency

- EasyInput assigns monotonically increasing non-zero u32 sequences and skips zero after wrap.
- Only one request may be in flight.
- A request waits 250 ms. It is retransmitted at most twice with identical bytes and sequence, for three total attempts.
- Three consecutive requests that exhaust all attempts move the controller to disconnected/waiting state and clear peer-derived capability and status data.
- While disconnected, EasyInput attempts HELLO once per second. After HELLO it reads capabilities once for each peer boot ID and polls status every two seconds.
- A response or error must match the in-flight sequence and type; unmatched responses are ignored and counted.
- Xiaozhi caches the last eight completed request responses by controller boot ID, sequence, type and request fingerprint. An identical duplicate returns the cached bytes. Reusing a sequence with different request bytes returns `SEQUENCE_CONFLICT`.
- A changed peer boot ID invalidates cached peer data and increments the peer-restart diagnostic.
- `SET_AGENT_STATE` is never replayed after a disconnect or peer restart. The caller must issue a new transition with a new sequence.

## T08 safety boundary

T08 does not route desktop commands, write OLED pixels, drive PWM/servos, initialize Xiaozhi audio, or alter EasyInput input, LED, GPIO8, configuration, NVS or Host Action semantics.
